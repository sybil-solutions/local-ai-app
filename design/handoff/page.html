Which screen to show

The app keeps no screen state of its own for the main flow. It reads GET /api/state and picks the screen with the first rule that matches. Settings, Models, Usage and the other detail screens are ordinary navigation on top.

    __RESOLVE__

Run phases from engine.js. Under each phase is the screen it shows. Stop and Cancel call DELETE /api/runs/:port from any phase. Two failures the engine can report, "GPU not reaching Docker" and "Driver problem", plus the fallback "Did not start", use the same failure layout with failure.word and failure.line.

Every route the app needs. Exists means it is in server/index.js today. Extend means the route exists and needs new fields. New routes are to build. The server keeps no gateway: engines serve the model APIs on their own ports, and these routes only manage them.

Desktop

The fullscreen desktop app has a top bar (Home, Models, Agents, Machines, Usage, Settings) and shows the same screens as full pages. Home is the painting with the three picks along the bottom. Keys: 1 to 6 jump to a section, Esc goes back, ← → change the pick, Enter starts.

Open questions

Things the design shows that the build has to decide.

  • Where requests come from, without a gatewayEngines answer on their own ports, so the server never sees a request. It can read client addresses from engine access logs (vLLM and SGLang print them) or sample open connections on each port. The app name only exists where an engine logs the User-Agent; otherwise the row says "Unknown app". Device names come from tailscale whois.
  • Agent installs and updates differ by systemOmarchy installs through mise, Hermes ships with its own desktop app, others use npm or a script. The app needs one install and one update command per agent per system, kept with the agent list.
  • Model cards need the base model's repoThe registry's catalog.models[].hf is often the quantized repo or missing (Gemma 4, Qwen3.8-Flash-Next). Add the base repo to the registry. Nemotron 3.5 Lightning has no card at all; the screen says so.
  • Usage needs two finer countersTokens per model per day are stored today. Today's chart needs hourly buckets and This run needs a counter that starts with the run.
  • App updatesPick the release channel (GitHub Releases with electron-updater is the obvious one; the repo is private, so it needs a token or a public release repo). Engines live in Docker, so restarting the app never stops a model.
  • Your own pictureStored on the machine running Local AI. Another device showing that machine shows its picture. More artwork can be added to the Background list as data.
  • Sample data in the designAgent versions, the usage split by model, request sources, the app version and the Tailscale name are placeholders.
  • The phone appRuns one small model on the phone itself, outside this server. Its screens are here; its runtime is a separate piece of work.
